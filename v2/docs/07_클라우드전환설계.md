## 0. v1 → v2 전환 과정 요약 (팀원 공유용)

### v1이 뭐였냐

처음엔 **EXE 파일 하나**로 모든 걸 해결했습니다.

```
사용자 PC에서 HPDFS.exe 실행
    → 내 PC의 디스크 SMART 데이터 읽기 (smartctl)
    → ML 모델로 고장 확률 계산
    → 결과를 CSV 파일에 저장
    → Streamlit으로 내 PC 화면에서만 대시보드 표시
```

**왜 문제였냐:**
- 내 PC에서만 동작 → 다른 사람 PC 진단 불가
- 데이터가 CSV 파일에만 쌓임 → 공유·집계 불가
- 업데이트할 때마다 EXE 파일 다시 배포해야 함
- 서버가 없으니 확장 자체가 불가능

---

### v2에서 뭘 바꿨냐

**핵심 변화: 모든 기능을 서버로 이동하고, 각 PC에는 데이터 수집만 하는 경량 에이전트만 남김**

```
[각자의 PC]                      [서버]                  [브라우저]
에이전트 실행      →HTTP→        Nginx (포트 80)   ←접속←   누구나 접근
5분마다 자동                      ↓            ↓
SMART 수집               FastAPI          Streamlit
                         ML 예측           대시보드
                         결과 저장            ↑
                            ↓             조회
                        PostgreSQL
                       (DB 중앙 저장)
```

---

### 구체적으로 뭘 만들었냐

| 구성 요소 | 역할 | 위치 |
|----------|------|------|
| **에이전트** | 각 PC에서 5분마다 SMART 수집 → 서버로 HTTP 전송 | 각자 PC |
| **FastAPI** | 에이전트 데이터 수신 → ML 예측 → DB 저장 | 서버 |
| **PostgreSQL** | 모든 PC의 진단 이력 중앙 저장 | 서버 |
| **Streamlit** | 브라우저로 접속하면 보이는 대시보드 | 서버 |
| **Nginx** | 포트 80 하나로 API·대시보드 요청 분리 | 서버 |
| **Docker Compose** | 위 4개를 명령어 하나로 한 번에 실행 | 서버 |
| **Kubernetes** | Pod 장애 자동 재시작, 메모리 상한 관리 | 서버 |
| **GitHub Actions** | main 브랜치 push 시 자동 이미지 빌드 → Docker Hub 업로드 | 클라우드 |

---

### v1 vs v2 한 줄 비교

| | v1 | v2 |
|--|----|----|
| 실행 방법 | EXE 더블클릭 | `docker compose up` |
| 데이터 저장 | 내 PC CSV | 서버 PostgreSQL |
| 여러 PC 모니터링 | ❌ | ✅ (에이전트만 설치) |
| 대시보드 접근 | 내 PC에서만 | 브라우저로 누구나 |
| 업데이트 방법 | EXE 재배포 | `git push` 한 번 |
| 장애 대응 | 사람이 직접 재시작 | k8s 자동 재시작 |
| 테스트 | 없음 | pytest 21개 자동 검증 |

## 1. 전환 배경

| 항목 | v1 (현재) | v2 (목표) |
|------|-----------|-----------|
| 실행 방식 | `HPDFS.exe` 로컬 실행 | URL로 어디서든 접속 |
| 데이터 저장 | CSV 파일 (PC 종료 시 유실 가능) | PostgreSQL (영구 보존) |
| 모니터링 대상 | 실행 중인 PC 1대 | 여러 PC 동시 모니터링 가능 |
| 인프라 | 없음 | Docker + Kubernetes + CI/CD |
| 배포 방식 | ZIP 파일 전달 | GitHub push → 자동 배포 |
| 실무 유사도 | 낮음 | 현업 표준 스택 |

## 2. 핵심 제약 사항

> **smartctl은 반드시 실제 디스크가 연결된 로컬 PC에서 실행해야 한다.**

이 제약 때문에 "앱 전체를 클라우드로 올리는" 방식은 불가능하다.
**로컬 에이전트가 수집 → 클라우드 API로 전송** 구조가 필수다.

## 3. 목표 아키텍처

```
[로컬 PC — 경량 에이전트 (agent.py)]
  ① smartctl로 SMART 데이터 수집
  ② HTTP POST → Nginx 경유 → FastAPI 전송
  ③ start_agent.bat으로 ON/OFF (또는 Task Scheduler로 자동화)

            ↓ HTTP

[서버 — Nginx (포트 80)]
  ④ /api/* 요청 → FastAPI:8010으로 라우팅
  ⑤ /* 요청   → Streamlit:8501로 라우팅

            ↓

[서버 — FastAPI (포트 8010)]
  ⑥ SMART 데이터 수신
  ⑦ ML 예측 실행 (storage/battery/symptom)
  ⑧ PostgreSQL에 저장

            ↓

[서버 — PostgreSQL (포트 5432)]
  diagnosis_log 테이블 (진단 이력)
  disks 테이블 (현재 상태 캐시)

            ↓

[서버 — Streamlit (포트 8501)]
  ⑨ GET /api/disks → 대시보드 렌더링
  ⑩ 어디서든 URL로 접속 가능
```

## 4. Docker Compose 통합 구조

```
docker-compose.yml
  services:
    postgresql   ← DB 컨테이너 (postgres:15-alpine)
    backend      ← FastAPI 컨테이너 (python:3.11-slim)
    frontend     ← Streamlit 컨테이너 (python:3.11-slim)
    nginx        ← 리버스 프록시 (nginx:alpine)
  networks:
    pdfs-network ← 서비스 간 내부 통신
```

### Nginx 라우팅 규칙 (nginx/nginx.conf)

```nginx
upstream backend {
    server backend:8010;
}

upstream frontend {
    server frontend:8501;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://backend;
    }

    location / {
        proxy_pass http://frontend;
    }
}
```

## 5. Kubernetes 배포 구조

```
k8s/
├── namespace.yaml          → pdfs 네임스페이스
├── configmap.yaml          → 환경변수 (DB URL 등 비민감 설정)
├── secret.yaml             → 민감 정보 (DB 비밀번호 Base64 인코딩)
├── postgres-deployment.yaml → PostgreSQL Pod (replicas: 1)
├── postgres-service.yaml   → DB 클러스터 내부 노출
├── backend-deployment.yaml → FastAPI Pod (replicas: 2)
├── backend-service.yaml    → FastAPI 클러스터 내부 노출
├── frontend-deployment.yaml → Streamlit Pod (replicas: 1)
├── frontend-service.yaml   → Streamlit 클러스터 내부 노출
├── nginx-deployment.yaml   → Nginx Pod (replicas: 1)
└── ingress.yaml            → 외부 트래픽 진입점 (포트 80)
```

### K8s 핵심 개념

| 개념 | 역할 | 예시 |
|------|------|------|
| Pod | 컨테이너 실행 단위 | FastAPI 1개 인스턴스 |
| Deployment | Pod 수 관리·재시작 | FastAPI 2개 유지 |
| Service | Pod 내부 통신 | backend:8010 |
| Ingress | 외부 트래픽 진입 | http://서버IP → Nginx |
| ConfigMap | 환경변수 관리 | DATABASE_URL |
| Secret | 민감정보 관리 | DB 비밀번호 |

## 6. GitHub Actions CI/CD 파이프라인

```yaml
# .github/workflows/deploy.yml (실제 구현)
name: Build & Push Docker Images

on:
  push:
    branches: [main]

jobs:
  build-and-push:
    steps:
      - Docker Hub 로그인 (Secrets: DOCKER_USERNAME, DOCKER_PASSWORD)
      - backend 이미지 빌드 & push (melooong/pdfs-backend:latest + git SHA)
      - frontend 이미지 빌드 & push (melooong/pdfs-frontend:latest + git SHA)
      - nginx 이미지 빌드 & push (melooong/pdfs-nginx:latest + git SHA)
```

> **참고:** 서버 자동 배포(SSH pull)는 미구현. Docker Hub push까지 자동, 서버 반영은 수동 `docker pull`.

### 흐름 요약

```
git push main
    ↓ (자동 트리거)
GitHub Actions (ubuntu 서버)
    ↓
Docker 이미지 3개 빌드
    ↓
Docker Hub에 latest + git SHA 태그로 push
    ↓ (수동)
서버에서 docker pull → 서비스 재시작
```

## 7. API 엔드포인트 설계

| 엔드포인트 | 메서드 | 역할 |
|-----------|--------|------|
| `/api/diagnose` | POST | SMART 수신 → ML 예측 → DB 저장 |
| `/api/disks` | GET | 전체 디스크 현재 상태 조회 |
| `/api/disks/{serial}` | GET | 특정 디스크 진단 이력 (최근 30건) |
| `/api/disks/{serial}/status` | PATCH | 조치 상태 변경 (F-08) |
| `/api/demo` | POST | 더미 데이터 주입 (발표용 7개) |

## 8. DB 테이블 설계 (PostgreSQL)

### diagnosis_log (진단 이력)

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | SERIAL PK | - |
| timestamp | TIMESTAMP | 진단 시각 |
| device | VARCHAR | 디바이스 경로 |
| model | VARCHAR | 모델명 |
| capacity_bytes | BIGINT | 용량 |
| smart_5_raw ~ smart_199_raw | INTEGER | SMART 8개 피처 |
| ml_probability | FLOAT | ML 예측 확률 |
| ml_level | VARCHAR | ML 등급 |
| rule_level | VARCHAR | 규칙 등급 |
| final_level | VARCHAR | 최종 등급 |

### disks (현재 상태 캐시)

| 컬럼 | 타입 | 설명 |
|------|------|------|
| serial | VARCHAR PK | 디바이스 경로 (시리얼 대용) |
| model | VARCHAR | 모델명 |
| capacity_bytes | BIGINT | 용량 |
| final_level | VARCHAR | 최신 등급 |
| risk | FLOAT | 최신 위험도 % |
| action_status | VARCHAR | 미확인 / 확인됨 / 조치완료 (F-08) |
| last_updated | TIMESTAMP | 마지막 진단 시각 |

## 10. 기존 코드 재사용 전략

클라우드 전환 시 기존 `app_hpdfs_portable.py`에서 재사용 가능한 함수:

| 함수 | 이전 위치 | 이전 후 위치 | 변경 여부 |
|------|-----------|-------------|-----------|
| `scan_devices()` | Streamlit 앱 | agent/smart_collector.py | 변경 없음 ✅ |
| `extract_features()` | Streamlit 앱 | agent/smart_collector.py | 변경 없음 ✅ |
| `predict()` | Streamlit 앱 | backend/predictor.py | 변경 없음 ✅ |
| `rule_level()` | Streamlit 앱 | backend/predictor.py | 변경 없음 ✅ |
| `reasons_actions()` | Streamlit 앱 | backend/predictor.py | 변경 없음 ✅ |
| `render_*()` | Streamlit 앱 | frontend/app.py | API 호출로 데이터만 교체 |
| `demo_disks()` | Streamlit 앱 | backend/router_disks.py | 변경 없음 ✅ |

> **핵심:** ML 예측 로직은 한 줄도 재작성할 필요 없다. 데이터 소스만 "함수 직접 호출"에서 "HTTP API"로 바꾸는 것이 전환의 전부다.
