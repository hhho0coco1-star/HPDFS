❌ 문제 상황
ML 모델만으로는 위험 디스크를 3개 중 1개밖에 못 잡는다
GradientBoosting 모델의 Recall이 0.34에 불과해 위험 디스크 10개 중 6~7개를 정상으로 잘못 판정. 고장 예측 시스템의 핵심 지표가 기준치 이하였습니다.
위험 클래스 Recall : 0.34  ← 고장 탐지 실패율 66%
🔍 원인 분석
데이터 불균형 — 정상:고장 = 200:1
Backblaze 데이터셋 특성상 고장 디스크는 전체의 0.5% 미만. "전부 정상"으로 예측해도 Accuracy 99%가 나오기 때문에 모델이 고장 패턴을 학습할 유인이 없었습니다.
✅ 해결 방법 — ML + 규칙 기반 하이브리드 예측 도입 (두 결과 중 더 높은 위험 등급 채택)
BEFORE ML 단독 판정
def predict(df, model):
    prob = model.predict_proba(df)[0][1]
    return prob_to_level(prob)
    # Recall 0.34 → 위험 66% 놓침
→
AFTER 하이브리드 판정
def rule_level(row):
    if row["smart_197_raw"] > 0 or row["smart_198_raw"] > 0:
        return "위험"   # 대기섹터·정정불가
    if row["smart_5_raw"] >= 100 or row["smart_187_raw"] > 0:
        return "위험"
    if row["smart_194_raw"] >= 50:
        return "주의"
    return "정상"

def predict(df, model):
    ml_lv   = prob_to_level(model.predict_proba(df)[0][1])
    rule_lv = rule_level(df.iloc[0])
    return combine_level(ml_lv, rule_lv)  # max 취합
📈 결과 및 교훈
SMART 치명 지표(대기섹터·정정불가)가 1 이상이면 ML 확률 무관하게 위험 판정. 고장 예측은 False Negative(놓침)가 False Positive(오경보)보다 치명적이므로 보수적 판정이 올바른 설계.

❌ 문제 상황
kubectl apply 후 진단 이력 데이터가 전부 사라짐
Pod 재시작 또는 재배포 시마다 PostgreSQL 데이터가 초기화되는 문제. 에이전트가 며칠간 수집한 이력이 반복적으로 삭제되었습니다.
재시작 후 SELECT COUNT(*) FROM diagnosis_log;
→ count = 0  ← 전체 소멸
🔍 원인 분석
컨테이너 내부 파일시스템은 Pod 생명주기와 함께 휘발
K8s Pod는 Stateless가 기본 설계. PostgreSQL 데이터 디렉터리(/var/lib/postgresql/data)가 컨테이너 레이어에 존재해 Pod 삭제 시 함께 삭제됩니다.
✅ 해결 방법 — PersistentVolumeClaim으로 DB 데이터 디렉터리를 Pod 바깥에 영속화
BEFORE Volume 없음 — 데이터 휘발
# postgres-deployment.yaml
containers:
  - name: postgresql
    image: postgres:15-alpine
    env:
      - name:  POSTGRES_DB
        value: hpdfs
        # volumeMounts 없음
    # → Pod 재시작 시 /var/lib/postgresql/data 초기화
→
AFTER PVC 마운트 — 데이터 영속
# postgres-pvc.yaml
apiVersion: v1
kind:       PersistentVolumeClaim
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 1Gi

# postgres-deployment.yaml
volumeMounts:
  - mountPath: /var/lib/postgresql/data
    name:      postgres-storage
volumes:
  - name: postgres-storage
    persistentVolumeClaim:
      claimName: postgres-pvc
📈 결과 및 교훈
Pod 재시작·재배포 후에도 PostgreSQL 데이터 완전 보존. K8s에서 Stateful 서비스는 반드시 PVC로 데이터를 외부화해야 한다는 것을 체득.
✅ 데이터 영속성 확보 ✅ Pod 재배포 무중단 ✅ Stateful 서비스 이해
❌ 문제 상황
Nginx 적용 후 Streamlit 화면이 로드되지 않음
Docker Compose에 Nginx 리버스 프록시를 추가했더니 Streamlit 대시보드가 흰 화면(502)으로 표시되거나 연결이 즉시 끊김. FastAPI는 정상 동작.
WebSocket connection failed: Connection closed
before receiving a handshake response
🔍 원인 분석
Streamlit은 WebSocket 기반 — Nginx 기본 설정은 HTTP/1.0
Streamlit은 실시간 UI 업데이트를 위해 WebSocket 프로토콜을 사용합니다. Nginx 기본 설정이 HTTP/1.0으로 동작하며 Upgrade·Connection 헤더를 upstream에 전달하지 않아 핸드셰이크가 실패.
✅ 해결 방법 — nginx.conf에 WebSocket 프록시 헤더 3줄 추가
BEFORE WebSocket 헤더 없음
location / {
    proxy_pass    http://frontend:8501;
    proxy_set_header Host $host;

        # WebSocket 관련 설정 없음
    # → 핸드셰이크 실패 / 502 Bad Gateway
}
→
AFTER WebSocket upgrade 헤더 추가
location / {
    proxy_pass           http://frontend:8501;
    proxy_set_header     Host $host;
    proxy_http_version   1.1;
    proxy_set_header     Upgrade $http_upgrade;
    proxy_set_header     Connection "upgrade";
}
💡 FastAPI는 왜 정상이었나?
FastAPI(REST API)는 요청-응답 방식의 HTTP/1.0으로도 동작합니다.

WebSocket을 사용하는 Streamlit만 upgrade 헤더가 필수입니다.

WebSocket 기반 서비스(Streamlit, Socket.IO 등)는 Nginx 프록시 시 항상 이 3줄이 필요합니다.
📈 결과 및 교훈
헤더 3줄 추가만으로 Streamlit 정상 렌더링. WebSocket 기반 서비스는 Nginx 프록시 시 반드시 upgrade 헤더가 필요하다는 것을 습득.
✅ Streamlit 정상 렌더링 ✅ WebSocket 프록시 이해 ✅ Nginx 설정 내재화
❌ 문제 상황
일부 디스크에서 온도 수집 실패 — AttributeError
에이전트 실행 중 특정 SSD 모델에서 SMART 수집이 실패해 에이전트가 중단. HDD는 정상이지만 일부 SSD에서 반복 오류가 발생.
AttributeError: 'dict' object has no attribute ...
Samsung SSD: "temperature": {"current": 35} ← dict
🔍 원인 분석
smartctl JSON 포맷이 제조사마다 다름
• HDD: "temperature": 41 (정수)
• SSD: "temperature": {"current": 35} (딕셔너리)

정수로만 처리하는 코드가 딕셔너리 형태를 만나 AttributeError 발생.
✅ 해결 방법 — isinstance()로 타입을 먼저 확인 후 분기 처리
BEFORE 타입 구분 없음
def _parse_temperature(self, data):
    temp = data.get("temperature")

        # 타입 확인 없이 그대로 반환
    # → dict이 들어오면 AttributeError!
    return temp
→
AFTER isinstance() 타입 분기
def _parse_temperature(self, data):
    temp = data.get("temperature")

    if isinstance(temp, dict):         # SSD
        return temp.get("current", 0)
    if isinstance(temp, (int, float)):  # HDD
        return int(temp)
    return 0  # 파싱 불가 → 기본값
📈 결과 및 교훈
HDD·SSD·NVMe 등 모든 디스크 타입에서 온도 정상 수집. 에이전트 중단 없이 안정 동작. 외부 툴 JSON은 버전·제조사마다 스펙이 달라 타입 체크와 fallback이 필수.
✅ 전 디스크 온도 수집 ✅ 에이전트 안정성 확보 ✅ 방어적 파싱 패턴
❌ 문제 상황
수동 진단 결과가 대시보드 디스크 목록에 계속 쌓임
발표 시연 중 수동 진단을 반복 실행하자 "MANUAL" 시리얼 디스크가 대시보드에 계속 추가되어 실제 모니터링 디스크와 섞이는 데이터 오염 발생.
대시보드 목록: WD-WCC4N... 위험 / ZA15TBZS 주의
MANUAL 위험 ← 오염 / MANUAL 정상 ← 중복 오염
🔍 원인 분석
수동 진단도 일반 진단과 동일하게 DB에 저장됨
POST /api/diagnose 엔드포인트가 serial 값에 무관하게 모든 요청을 DiagnosisLog와 Disk 테이블에 저장. 설계 시 수동/자동 구분 로직이 없었습니다.
✅ 해결 방법 — serial == "MANUAL" 조건으로 DB 저장 로직 스킵, 예측 결과만 반환
BEFORE 구분 없이 전체 저장
@router.post("/api/diagnose")
async def diagnose(data: SmartData, db: Session):
    result = predict(df, model)

        # serial 값 구분 없이 항상 저장
    db.add(DiagnosisLog(**data.dict()))
    upsert_disk(db, data, result)
    db.commit()
    return result
→
AFTER MANUAL이면 저장 스킵
@router.post("/api/diagnose")
async def diagnose(data: SmartData, db: Session):
    result = predict(df, model)

    if data.serial != "MANUAL":  # 수동 진단 제외
        db.add(DiagnosisLog(**data.dict()))
        upsert_disk(db, data, result)
        db.commit()
    return result  # 예측 결과는 항상 반환
📈 결과 및 교훈
수동 진단을 아무리 반복해도 대시보드 데이터에 영향 없음. 발표 중 자유로운 반복 시연 가능. 테스트·시연 입력은 운영 데이터와 명확히 분리 설계해야 함.
✅ 대시보드 오염 방지 ✅ 반복 시연 자유로움 ✅ 관심사 분리 설계
