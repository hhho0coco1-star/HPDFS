## 1. 데이터 분석 결과 (실측)

확인 파일: `data/2016-03-02.csv` (Backblaze Drive Stats 하루치, 15.5MB)

| 항목 | 값 |
|------|-----|
| 전체 컬럼 수 | **95개** (기본정보 5개 + SMART 90개) |
| 첫 5개 컬럼 | `date, serial_number, model, capacity_bytes, failure` |
| SMART 컬럼 형태 | `smart_[번호]_normalized`, `smart_[번호]_raw` 쌍 반복 |
| 디스크 수(행) | **62,415개** |
| 당일 고장(`failure=1`) | **4개** |
| 고장 비율 | **0.0064%** (극단적 불균형) |
| 결측치 | smart_5_raw 기준 빈칸 0개 (단, 컬럼마다 다를 수 있음) |

> **핵심 발견:** 하루에 고장이 4개뿐. 이 데이터 불균형이 PDFS의 가장 큰 기술적 숙제이자 실력 포인트.

## 2. 데이터 범위 결정 — 1분기

| 데이터 양 | 예상 고장 샘플 | 평가 |
|----------|--------------|------|
| 하루치 | 4개 | 학습 불가 |
| **1분기 (~90일)** | **약 450개** (재라벨링 시 약 13,000개) | ✅ **채택** |
| 1년치 | 수천 개 | 초보 팀엔 과함(무겁고 느림) |

**결정:** 학습 데이터는 **1분기 사용**.

- 1분기 ≈ CSV 90개 ≈ 압축 해제 시 약 12GB ≈ 약 540만 행.
- ※ 예상 고장 수는 하루치(4개) 기반 추정. 실제 분기를 받아 세면 정확해짐.

## 3. 전처리 방향

### 3-1. 핵심 컬럼만 추출
95개 컬럼을 모두 쓰지 않고, 고장 예측에 강한 컬럼만 남긴다.
**실제 예측 스크립트(`storage_auto_predict_v3`)가 사용하는 피처 = 다음 10개:**

| 피처 | 의미 |
|------|------|
| `model` | 디스크 모델명 |
| `capacity_bytes` | 용량 |
| `smart_5_raw` | 재할당 섹터 수 |
| `smart_9_raw` | 가동 시간(Power-On Hours) |
| `smart_187_raw` | 정정불가 에러 보고 |
| `smart_188_raw` | 명령 타임아웃 |
| `smart_194_raw` | 온도(℃) |
| `smart_197_raw` | 대기(보류) 섹터 수 |
| `smart_198_raw` | 오프라인 정정불가 섹터 |
| `smart_199_raw` | UDMA CRC 에러 수 |

- 학습 시에는 여기에 `failure`(정답 라벨)를 더해 사용한다.
- 효과: 데이터 경량화, 노이즈 제거로 정확도 향상, 처리 속도 향상
- 담당: 컬럼 선정=데이터분석(김응석), 저장·관리=인프라(안세웅)

### 3-2. 라벨 재정의 (중요)
`failure=1`은 "고장난 당일"만 표시되어 있다. 이대로 쓰면 예측이 아니라 사후 확인이 된다.
- → **"고장 N일 전(예: 7일/30일)부터 위험"으로 재라벨링**하여 "미리 예측"하는 모델로 만든다.
- 담당: 데이터분석(김응석)

### 3-3. 학습/평가 분할
시계열 데이터이므로 무작위 분할이 아니라 **시간순 분할**한다.
- 예: 앞 2개월=학습, 마지막 1개월=평가

### 3-4. 불균형 처리
재라벨링 후에도 위험 비율 약 0.25%로 불균형이 남는다.
- class weight, 오버/언더샘플링 등 기법 적용 필요.

## 4. 모델 선택 — GradientBoosting

### 4-1. 모델 비교 결과 (7개, `storage` 데이터)

고장(`failure_1`) 기준 핵심 지표:

| 모델 | Recall(고장 잡기) | Precision(경보 정확) | F1(균형) | ROC_AUC |
|------|:---:|:---:|:---:|:---:|
| **GradientBoosting** ✅ | 0.34 | **0.85** | **0.49** | 0.82 |
| Bagging | 0.37 | 0.66 | 0.48 | 0.81 |
| RandomForest | 0.36 | 0.69 | 0.47 | 0.84 |
| KNN | 0.28 | 0.68 | 0.40 | 0.69 |
| DecisionTree | 0.33 | 0.35 | 0.34 | 0.66 |
| LogisticRegression | 0.67 | 0.14 | 0.23 | 0.87 |
| SVM | 0.60 | 0.13 | 0.21 | 0.86 |

> Accuracy는 전 모델 0.99이지만 불균형 때문에 무의미. `failure_1` 지표로 판단한다.
> 최적 파라미터: `learning_rate=0.1, n_estimators=100`

### 4-2. 선택 근거
- **GradientBoosting 채택** (데이터분석 김응석 판단).
- 균형 점수(F1) 7개 중 1위, 경보 정확도(Precision 0.85)가 높아 거짓 경보가 적음.
- 학습 후 모델이 가볍고 추론이 빨라 서빙·배포 부담이 적음(인프라 유리).

### 4-3. 단일 모델 사용 (앙상블 미적용)
- GradientBoosting 자체가 트리 수백 개를 합친 앙상블 모델이다.
- 서로 다른 모델을 추가로 섞는 것(Voting/Stacking)은 복잡도·속도 부담 대비 효과가 불확실하여 **사용하지 않는다.**
- 초보 팀 기준 "단일 모델을 제대로"가 유지보수·설명·배포 모두 유리.

### 4-4. 개선 과제 — Recall
- 단일 모델 기준 Recall 0.34 → 실제 고장의 약 2/3를 놓침. "고장 예측" 목표상 개선 필요.
- 개선 방법(모델 교체/섞기가 아님):
  1. 데이터를 1분기로 늘리기 (고장 샘플 증가) — 효과 가장 큼
  2. 임계값(경보 기준) 조정
  3. 불균형 처리 기법 적용
  4. **규칙 기반 보완 (이미 코드에 구현됨 → 4-5 참고)** — Recall 문제의 1차 해결책

### 4-5. ML + 규칙 기반 하이브리드 판정 (실제 코드 반영)

예측 스크립트(`storage_auto_predict_v3`)는 ML 확률 단독이 아니라 **ML 등급과 규칙 기반 등급 중 더 높은 쪽을 최종 채택**한다. ML이 고장을 놓쳐도(낮은 Recall) 실제 위험 SMART 신호는 규칙이 무조건 잡아내, Recall 문제를 실질적으로 보완한다.

**위험 등급 임계값 (ML 확률 기준):**

| 등급 | 조건 |
|------|------|
| 정상 | 확률 < 0.3 |
| 주의 | 0.3 ≤ 확률 < 0.7 |
| 위험 | 확률 ≥ 0.7 |

**규칙 기반 강제 판정 (ML 확률과 무관):**

| 조건 | 등급 |
|------|------|
| 대기섹터(197) > 0 또는 정정불가(198) > 0 | 위험 |
| 재할당섹터(5) ≥ 100 | 위험 |
| 정정불가 에러(187) > 0 | 위험 |
| 재할당(5)/CRC(199)/명령타임아웃(188) > 0 | 주의 |
| 온도(194) ≥ 50℃ | 주의 |

→ **최종 등급 = max(ML 등급, 규칙 등급).** 추가로 SMART 값별 예상 원인과 권장 조치를 자동 생성한다(디스크 상세 화면의 "예측 근거·권장 조치"에 대응).

## 5. 목표 눈높이

- 목표는 "완벽한 예측"이 아니라 **"고장 위험을 미리 경고"**.
- 현재 모델 성능은 출발점이며, 데이터·전처리·임계값 튜닝으로 개선해 나간다.
